# 数据库分发管控服务 Vibe Coding 开发约束

> 状态：分支级开发基线  
> 适用范围：本仓库全部代码、配置、文档、测试、数据库迁移、部署脚本和 AI 编码任务  
> 核心原则：用 AI 的速度扩大验证覆盖，而不是用 AI 的速度扩大未经验证的代码量。

## 1. 为什么需要这份约束

Vibe Coding 的主要风险不是“代码由 AI 生成”，而是开发过程容易出现以下失控：

- 在需求和架构尚未冻结时快速堆叠实现；
- 生成大量表面完整、边界含混的代码；
- 通过 Mock、固定返回或弱化断言制造“测试通过”；
- 把一次性演示代码误当作可长期维护的服务；
- 代码、契约、数据库结构、部署配置产生多套事实；
- 未经真实验证就声称性能、安全性和可靠性达标。

因此，本项目不以“人工逐行读懂所有代码”作为唯一质量手段，而采用 **契约化、自动化、多模型复核、故障注入和证据化交付** 的工程方式，把效率优势转化为质量优势。

## 2. 开发基本原则

### 2.1 单一事实来源

每类事实只能有一个权威来源：

| 事实类型 | 权威来源 |
|---|---|
| 服务职责与边界 | `docs/architecture/` |
| API 输入输出 | OpenAPI / JSON Schema / protobuf 等契约文件 |
| 数据结构 | 迁移脚本与 Schema |
| 运行配置 | 类型化配置定义与示例配置 |
| 行为正确性 | 自动化测试与验收证据 |
| 开发约束 | `AGENTS.md` 与本文件 |

README、代码注释和汇报材料不得创造与权威来源冲突的新事实。

### 2.2 最小变更

每个任务必须明确：

- 本次要解决的问题；
- 涉及的模块；
- 明确不做的内容；
- 兼容性影响；
- 验证方式。

禁止借任务之名进行无关重构、依赖升级、目录改造或技术栈替换。

### 2.3 契约先于实现

新功能实施顺序：

1. 场景和边界；
2. 请求/响应/错误 Schema；
3. 状态机与幂等语义；
4. 测试用例；
5. 实现；
6. 真实集成验证；
7. 文档与证据归档。

### 2.4 失败关闭

当租户、业务域、权限、路由目标、Schema、配置或 Secret 不明确时，系统必须拒绝执行，不得猜测默认值继续运行。

## 3. 数据库分发管控服务的架构护栏

根据当前架构资料，服务包含两类调用路径：

1. 业务系统或本体服务通过统一业务接口调用；
2. Agent/OpenClaw 通过 Data Access Gateway 的 Tool 协议调用，再转换为统一 DataRequest。

两类路径进入核心服务后必须共用同一套：

- 请求 Schema 校验；
- `tenant_id + biz_domain` 上下文解析；
- RBAC/ABAC 权限判断；
- 幂等检查；
- operation 与 target 路由；
- Adapter 执行；
- Access Audit 与 Change Audit；
- DataResponse 统一封装。

禁止维护两套权限、路由、审计或错误处理逻辑。

### 3.1 服务允许做什么

- 校验标准化数据请求；
- 解析可信租户和业务域上下文；
- 判断调用者是否有权访问逻辑资源；
- 将逻辑目标映射到允许的数据源；
- 调用相应 Adapter；
- 实施幂等、限流、超时、重试、熔断；
- 记录访问与变更审计；
- 返回统一响应和稳定错误码。

### 3.2 服务禁止做什么

- 承载案件、用户、订单等具体业务规则；
- 接受客户端任意数据库连接信息；
- 暴露数据库账号、物理地址或 SDK 原始对象；
- 绕过租户边界执行“管理员兜底查询”；
- 默认支持任意 SQL、Cypher 或脚本执行；
- 把跨源写入包装成不存在的强事务；
- 在日志中记录完整请求体或敏感返回值；
- 成为各业务系统可随意使用的通用数据库代理。

## 4. AI 编码任务输入模板

交给 Codex 或其他编码代理的任务必须包含：

```text
任务目标：
业务背景：
允许修改的目录：
禁止修改的目录：
输入契约：
输出契约：
租户与权限要求：
幂等要求：
失败语义：
性能目标：
测试要求：
真实依赖与环境：
非目标：
完成证据：
```

缺失关键字段时，编码代理只能进行只读分析并提出问题，不得直接实施大范围修改。

## 5. 实施阶段门禁

### Gate 0：仓库预检

必须记录：

- 当前分支与基线提交；
- 工作区是否干净；
- 相关目录和既有约束；
- 当前测试基线；
- 是否存在 Secret 或本地专用配置；
- 架构文档与代码是否存在冲突。

### Gate 1：设计冻结

至少产出：

- 模块边界；
- 请求/响应 Schema；
- 错误码；
- 状态机；
- 数据模型与索引；
- 幂等作用域；
- 安全与租户隔离设计；
- 测试矩阵。

### Gate 2：最小实现

要求：

- 只实现冻结范围；
- 禁止提前抽象未知扩展点；
- 禁止复制数据库厂商类型到领域层；
- 禁止静默 fallback；
- 配置必须类型化并在启动时校验。

### Gate 3：自动化验证

至少执行：

- format/lint；
- 类型检查；
- 单元测试；
- 契约测试；
- 集成测试；
- 迁移测试；
- Secret 扫描；
- 依赖漏洞检查；
- 关键路径并发和故障测试。

### Gate 4：独立复核

复杂变更至少进行一次独立复核，可由另一模型或另一开发者完成，重点检查：

- 是否偏离架构；
- 是否存在跨租户路径；
- 是否错误承诺事务语义；
- 是否存在未覆盖的失败路径；
- 测试是否在验证真实行为；
- 是否把内部实现泄漏给调用方。

### Gate 5：交付证据

完成报告必须区分：

- 已实现；
- 已自动测试；
- 已真实环境验证；
- 尚未验证；
- 已知风险与技术债。

所有命令结果必须来自真实执行。禁止生成看似真实的虚构日志。

## 6. 代码质量约束

### 6.1 结构

- 领域和应用代码不得导入具体数据库 SDK；
- Adapter 与目标数据源一一对应；
- 公共逻辑通过组合复用，不建立“万能 BaseAdapter”；
- 函数保持单一职责；
- 复杂分支优先使用显式状态机或策略表；
- 不允许同一概念使用多组名称。

### 6.2 类型与校验

- 外部输入一律视为不可信；
- 所有输入必须在边界处运行时校验；
- 禁止仅依赖 TypeScript/静态类型保证运行时安全；
- 枚举值必须封闭；
- 时间、金额、分页、路径和标识符必须有明确格式；
- 未知字段的处理策略必须明确，安全敏感接口优先拒绝未知字段。

### 6.3 数据库操作

- 使用参数化查询；
- 查询必须有租户条件或由物理隔离保证；
- 大结果集必须分页或流式；
- 写操作必须设置超时；
- 禁止无界扫描、无界批量写入和 `SELECT *` 进入公共接口；
- 索引必须与真实查询模式相匹配；
- Schema 变更必须通过迁移脚本。

### 6.4 配置与 Secret

- `.env` 真实文件不得提交；
- 提交 `.env.example` 时只能放占位符；
- 日志必须对 Authorization、Cookie、Token、密码、连接串等字段进行递归脱敏；
- 测试中的假 Secret 必须明显为测试值；
- 错误响应不得回显下游连接信息。

## 7. 测试矩阵

每个 operation 至少覆盖以下维度：

| 维度 | 必测场景 |
|---|---|
| 正常路径 | 合法请求成功并返回标准响应 |
| Schema | 缺字段、错类型、未知枚举、超限输入 |
| 租户隔离 | 缺 tenant、错 tenant、跨 tenant 资源 |
| 业务域隔离 | 错 biz_domain、跨域路由 |
| 权限 | 无身份、权限不足、资源级拒绝 |
| 幂等 | 首次、重复同请求、重复不同请求、处理中重试 |
| 并发 | 同键并发、同资源并发、连接池耗尽 |
| 下游故障 | 超时、断网、限流、部分失败、不可重试错误 |
| 审计 | 成功、拒绝、失败均有审计且无 Secret |
| 恢复 | 重启后幂等状态和未完成任务处理正确 |

Adapter 契约测试必须确保不同 Adapter 对同一领域错误使用同一错误码，而不是暴露不同数据库的原始异常。

## 8. 反作弊测试规则

以下行为视为测试造假：

- `skip`、`only`、注释失败用例；
- 把严格断言改成只判断非空；
- 在生产代码识别测试环境后返回特殊结果；
- 用 Mock 替代任务明确要求的真实服务；
- 捕获异常后无条件返回成功；
- 测试只验证函数被调用，不验证结果和副作用；
- 删除失败路径测试来维持覆盖率；
- 将覆盖率数字作为正确性的替代品。

发现既有测试错误时，必须先说明测试为何错误，并用契约或外部事实证明，才能修改。

## 9. 性能与稳定性声明规则

只有在以下条件具备时才能声明性能结果：

- 固定测试数据和环境；
- 明确并发、请求模型和持续时间；
- 记录 P50/P95/P99、吞吐、错误率和资源占用；
- 同基线版本对比；
- 重复执行并说明波动。

禁止仅凭局部代码优化、单次运行或 Mock 数据声称服务“高性能”“生产可用”。

## 10. Git 与提交约束

- 一个提交只表达一个逻辑变化；
- 提交信息说明变更目的，不只写“update”或“fix”；
- 禁止把生成物、日志、数据库文件、IDE 配置和 Secret 提交；
- 禁止 force push 覆盖他人工作，除非用户明确授权；
- 未经用户要求不直接合并 main；
- 架构基线、契约和迁移变更应独立提交，便于审计与回滚。

## 11. 技术债管理

无法在当前任务解决的问题必须登记，而不是隐藏：

```text
债务编号：
问题描述：
产生原因：
影响范围：
当前缓解措施：
触发修复条件：
建议方案：
```

禁止使用模糊 TODO。TODO 必须关联任务、责任边界或明确触发条件。

## 12. Definition of Done 检查表

- [ ] 任务边界和非目标已记录
- [ ] 架构与契约已更新
- [ ] 多租户和权限路径已验证
- [ ] 写操作幂等与并发语义已验证
- [ ] 下游故障和恢复路径已验证
- [ ] Adapter 未泄漏供应商类型
- [ ] 审计完整且通过 Secret 扫描
- [ ] 迁移可执行并有恢复说明
- [ ] 单元、契约、集成测试真实通过
- [ ] 无跳过测试、固定返回或临时绕过
- [ ] 完成报告区分事实、推断与未验证项
- [ ] 变更可回滚
