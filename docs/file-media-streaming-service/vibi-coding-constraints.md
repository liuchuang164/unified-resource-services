# 文件 / 音视频流式服务 Vibi Coding 开发约束

## 1. 目的

本约束用于把 AI 编码的速度优势转化为可验证的质量优势，防止出现：架构偏离、一次生成大量不可审查代码、接口与实现脱节、租户隔离遗漏、测试结果虚构以及技术债快速堆积。

本阶段只建立约束与架构基线，不开展业务实现。

## 2. 总体原则

1. **架构优先于代码**：先确认边界、契约、状态机和失败语义，再写实现。
2. **小步垂直切片**：每次只实现一个可独立验收的端到端能力。
3. **契约先行**：公共 API、事件、领域命令和错误码先定义并评审。
4. **测试先行或同步**：不得在实现完成后再补“装饰性测试”。
5. **证据化交付**：所有“已完成、已通过、已兼容”必须有命令、日志或测试报告支撑。
6. **多模型复核**：重要变更至少经过实现、审查、测试三个相互独立的 AI 角色或会话。
7. **不猜架构**：缺少关键决策时停止并报告，不得自行选择云服务、协议或存储模型。

## 3. 建议目录边界

具体语言和框架由后续技术决策确定，但逻辑边界必须保持：

```text
services/file-media-streaming-service/
├── AGENTS.md
├── contracts/              # OpenAPI / AsyncAPI / JSON Schema / Tool Schema
├── src/
│   ├── gateway/            # Agent tools 与业务 API 适配
│   ├── application/        # 用例编排、事务边界、权限协调
│   ├── domain/             # 实体、值对象、状态机、领域规则
│   ├── ports/              # 存储、队列、处理能力接口
│   ├── infrastructure/     # PostgreSQL / MinIO / Redis / Queue 实现
│   ├── providers/          # OCR / ASR / 视频 / 转码适配器
│   └── observability/      # 日志、指标、Trace、审计
├── tests/
│   ├── unit/
│   ├── contract/
│   ├── integration/
│   ├── isolation/
│   ├── failure-injection/
│   └── e2e/
└── docs/
```

禁止以框架默认目录为理由破坏上述逻辑分层。

## 4. 分阶段开发约束

### Phase 0：架构与契约

产物：

- 架构基线和上下文图；
- 模块边界；
- 领域对象与状态机；
- API / Tool / Event Schema；
- 错误码、幂等语义、租户上下文；
- ADR；
- 测试计划。

完成标准：没有业务实现，所有关键决策可评审。

### Phase 1：服务骨架

仅允许建立：

- 应用启动与健康检查；
- 配置加载与校验；
- 统一错误模型；
- Trace / 日志基础；
- 空实现端口；
- 单元测试和静态检查流水线。

不得接入真实对象存储或处理提供方。

### Phase 2：资源元数据最小闭环

实现资源创建、查询和权限检查，不上传二进制。要求先完成租户隔离、幂等和状态机测试。

### Phase 3：分片上传最小闭环

实现初始化、分片登记、完成、校验、终止和过期。必须覆盖重复分片、乱序、缺失分片、校验失败和并发完成。

### Phase 4：受控下载与访问授权

实现最小权限、短时效访问授权。不得返回永久公开地址。

### Phase 5：异步处理任务

先接入一个 Fake Provider 完成任务状态机，再逐个引入 OCR、ASR、转码或视频处理适配器。

### Phase 6：流式会话

只有在流协议、会话模型、资源预算和断线恢复策略确认后才可实施。

### Phase 7：恢复、清理与对账

覆盖 Worker 崩溃、重复消息、过期会话、孤儿对象、任务补偿和元数据—对象存储一致性对账。

### Phase 8：安全与容量验证

覆盖恶意文件、伪造 MIME、超限、并发、带宽、敏感日志、签名 URL 泄露面和跨租户攻击。

## 5. 每次编码任务的强制输入

Codex 或其他编码 Agent 开始前必须明确：

- 本次 Phase 与唯一目标；
- 允许修改的目录和文件；
- 明确禁止修改的范围；
- 输入契约与预期输出；
- 状态变化；
- 权限规则；
- 幂等键；
- 失败场景；
- 验收测试；
- 完成后需执行的命令。

缺少其中关键项时不得扩大实现范围。

## 6. 公共契约约束

- 统一采用版本化契约；
- `tenant_id`、`biz_domain`、`request_id`、`trace_id` 不得被业务参数覆盖；
- 错误响应必须机器可读，至少包含 `code`、`message`、`request_id`、`trace_id`；
- 重试安全的写操作必须定义幂等语义；
- 分页、排序、过滤必须有确定性；
- Provider 私有字段不得出现在公共 API；
- 事件必须包含事件 ID、聚合 ID、租户范围、版本和发生时间；
- 不兼容变更必须通过新版本而不是直接覆盖。

## 7. 数据和事务约束

- PostgreSQL 是资源、会话、任务状态的最终事实源；
- Redis 只能存短期状态、锁、限流和缓存；
- MinIO 只存二进制和派生产物，不承担权限事实源；
- 数据库记录与对象存储写入采用可恢复工作流，不假设分布式事务；
- 对象键必须由服务端生成，不直接使用用户文件名；
- 删除、过期和清理操作必须记录审计并可重复执行；
- 迁移必须向前兼容、可回滚或提供恢复方案；
- 禁止在无迁移、无测试的情况下修改持久化结构。

## 8. 安全约束

- 所有查询和写入必须强制租户与业务域过滤；
- 权限校验位于应用用例边界，不能只依赖网关；
- 文件类型需通过内容检测，不能只看扩展名；
- 文件名、元数据和回调地址必须防注入；
- 限制文件大小、分片数、流时长、并发数和处理预算；
- 签名 URL、上传凭证和回调密钥不得写入普通日志；
- 原始音视频和识别文本默认按敏感数据处理；
- 外部 Provider 请求只发送完成任务所需的最少数据；
- 所有 Secret 通过环境或 Secret Manager 注入；
- 禁止把真实凭证、内部地址或个人数据提交到仓库。

## 9. 测试矩阵

每个能力至少覆盖：

| 类别 | 必测内容 |
|---|---|
| 单元测试 | 领域规则、状态机、值对象、错误映射 |
| 契约测试 | API、Tool Schema、事件兼容性 |
| 集成测试 | PostgreSQL、MinIO、Redis、Queue 适配 |
| 隔离测试 | 不同 tenant / biz_domain 间不可见、不可修改 |
| 幂等测试 | 同一请求、重复事件、重复回调 |
| 并发测试 | 完成上传、取消任务、删除资源等竞态 |
| 故障注入 | 超时、网络断开、Worker 崩溃、存储失败 |
| 安全测试 | 路径穿越、MIME 伪造、越权、日志泄密 |
| 性能测试 | 分片并发、吞吐、任务堆积、流连接 |
| 恢复测试 | 重启恢复、孤儿对象、任务补偿、对账 |

不得只测试 HTTP 200 路径。

## 10. AI 多轮质量闭环

重要 Phase 使用三个独立角色：

1. **Builder**：依据契约和测试实现最小功能；
2. **Reviewer**：只审架构偏离、安全、并发、异常与可维护性，不替 Builder 辩护；
3. **Verifier**：独立生成并执行额外测试，重点攻击边界条件和错误假设。

若三者结论冲突，以可复现测试和架构源文档为准。

## 11. 提交与 PR 约束

每个提交必须：

- 单一目的；
- 不混入无关格式化；
- 提交信息说明模块与行为；
- 包含对应测试或文档；
- 不提交生成物、缓存、凭证和本地配置。

PR 描述至少包含：

- 目标与非目标；
- 架构映射；
- 状态机或契约变化；
- 安全与租户影响；
- 测试命令及结果；
- 已知风险；
- 回滚方式；
- 后续 Phase。

## 12. 完成定义

任务只有同时满足以下条件才可标记完成：

- 变更没有超出当前 Phase；
- 契约与代码一致；
- 所有必需测试真实执行并通过；
- 没有跨租户访问路径；
- 没有敏感信息进入日志或仓库；
- 状态机、失败与恢复语义明确；
- 文档已更新；
- 输出实际改动文件、命令、结果、风险和未完成项。

“代码生成完成”不等于“任务完成”。

## 13. 当前阶段验收

本约束阶段验收仅包括：

- 从 `main` 创建独立分支；
- 添加服务范围 `AGENTS.md`；
- 添加架构基线；
- 添加 Vibi Coding 开发与质量约束；
- 不创建服务实现代码；
- 等待原始架构包可读取后进行逐项校准。
